## Background

`v1.6.1` is the binary for the consensus-breaking `v1.6` upgrade that follows the `v1.5.x` line. The governance plan name is `v1.6`.

**On the `v1.6.x` line, deploy `v1.6.1` or higher.** `v1.6.0` is a pre-release and is not intended for network deployment.

Binaries are available from the [v1.6.1 release page](https://github.com/axelarnetwork/axelar-core/releases/tag/v1.6.1), from S3, and from Docker Hub (see [Prerequisites](#prerequisites)). The changes since `v1.5.5` are summarized below.

### Upgrade handler

At the upgrade height the `v1.6` handler:

- Runs the evm store migration (11 -> 12), which seeds the new per-chain `commandBatchSizeLimit` param on every registered EVM chain, deactivated chains included: `45000` for `linea*`, `49000` for `filecoin*`, `80000` for `arbitrum*`, `99000` for `scroll*`, and `110000` for every other chain.
- Raises the nexus `end_blocker_limit` and every EVM chain's `end_blocker_limit` to `300`, deactivated chains included ([#2444](https://github.com/axelarnetwork/axelar-core/pull/2444)). Setting them in the handler makes them take effect at the same height as the `ConfirmGatewayTxs` gas charge below.

No governance parameter changes are needed before or after the upgrade. The per-network sections below list the exact values each chain gets.

### Changes since v1.5.5

#### Emergency controls

- **Adds an emergency pause and halt to `x/permission`** ([#2440](https://github.com/axelarnetwork/axelar-core/pull/2440)). The pause rejects every transaction outside a per-level allowlist while blocks keep being produced. The halt schedules an upgrade plan at the next height, so every node stops before executing it. Both can be run by the governance key or a gov proposal. Validators can override either one if 2/3 of the voting power runs with `--unsafe-skip-halt-pause`.

#### EVM and nexus

- **Increases the gas charged for `ConfirmGatewayTxs`**, caps the events per vote at 75, and charges the shared setup cost once per tx ID ([#2391](https://github.com/axelarnetwork/axelar-core/pull/2391)).
- **Bounds each EVM command batch by encoded size as well as gas** ([#2432](https://github.com/axelarnetwork/axelar-core/pull/2432)). The bound is the new per-chain governance parameter `commandBatchSizeLimit`, seeded by the upgrade handler.
- **Rejects `RetryFailedMessage` while more than 30 messages are waiting to be routed**, and `RetryFailedEvent` while more than 30 events are waiting to be processed on that chain ([#2431](https://github.com/axelarnetwork/axelar-core/pull/2431)). Relayers and retry tooling should expect these rejections while the queues are backed up.
- Requires the IBC path passed to `AddCosmosBasedChain` to name an existing, open channel on the `transfer` port ([#2402](https://github.com/axelarnetwork/axelar-core/pull/2402)).

#### Transaction validation

- Bounds message wrapping to one level and binds every wrapped message to its wrapper's signer ([#2443](https://github.com/axelarnetwork/axelar-core/pull/2443)).
- Rejects transactions whose `TxRaw` encoding repeats `body_bytes` or `auth_info_bytes` ([#2430](https://github.com/axelarnetwork/axelar-core/pull/2430)).
- Lowers the nested `Any` depth cap from 10000 to 64 via the cosmos-sdk fork bump ([#2437](https://github.com/axelarnetwork/axelar-core/pull/2437)).

#### Signing

- Rejects a signature that another participant of the same signing session already submitted ([#2417](https://github.com/axelarnetwork/axelar-core/pull/2417)).
- Calls the module's `HandleFailed` whenever a signing session cannot be completed, including when `HandleCompleted` errors or panics ([#2426](https://github.com/axelarnetwork/axelar-core/pull/2426)).

#### Other

- Only allows deposits into the distribution community pool and validator rewards pools in denominations that can pay fees ([#2390](https://github.com/axelarnetwork/axelar-core/pull/2390)).
- `vald`: adds a `confirmation_if_ahead` value for the EVM `finality_override` ([#2433](https://github.com/axelarnetwork/axelar-core/pull/2433)), and lowers the default `max_batch_size` from 250 to 150 ([#2429](https://github.com/axelarnetwork/axelar-core/pull/2429)).
- Only renders block messages in `LogMsgDecorator` when debug logging is enabled ([#2435](https://github.com/axelarnetwork/axelar-core/pull/2435)).
- **Bumps Go to 1.26.10**, go-ethereum to v1.17.0 and dependencies ([#2441](https://github.com/axelarnetwork/axelar-core/pull/2441)), and **wasmd to v0.60.9 and wasmvm to v2.3.5** ([#2425](https://github.com/axelarnetwork/axelar-core/pull/2425)). This is why **`libwasmvm` moves from v2.3.4 to v2.3.5**.

`ampd` is **not** bumped for this upgrade. Verifier handlers continue against the same `ampd` version.

## Deployment Steps for Axelar Maintainers

Roll out in order: Devnet Amplifier, then Testnet (soak at least a week), then Mainnet.

Upgrade height = height at submission time + (seconds until target halt time / block time).

All three proposals are submitted as **expedited** (`"expedited": true` in the proposal file). Two things follow from that:

- **The deposit must be the expedited minimum**, paid in full at submission, so the proposal goes straight into voting.
- **An expedited proposal that misses the 66.7% threshold is not rejected.** It is converted to a normal proposal and its voting period is extended to the normal length (5m / 1h / 3 days). If the upgrade height falls before the extended voting end, the plan can no longer be scheduled when the proposal passes, and a new proposal with a later height is needed. Pick the height after the expedited voting end plus the comms window, and be ready to resubmit if the expedited vote fails.

### Upgrade Process

1. Wait for upgrade height to be reached. **Do not replace the binary before the halt.** The node must keep running `v1.5.x` all the way to the upgrade height, halt there on its own, and only then be restarted on `v1.6.1`.
2. Stop the validator `axelard` node and `vald`. `ampd` is not bumped and does not need to be restarted for the version change.
3. Replace the binaries:
   - `axelard` -> `v1.6.1`
   - `vald` -> `v1.6.1` (bundled in the same `axelard` build)
   - `tofnd` -> `v1.0.1` (no change vs. v1.5.x)
   - `libwasmvm` -> `v2.3.5` (dynamic binary and source builds only)
4. No `app.toml` / `config.toml` changes are required relative to a node already running `v1.5.x`. `vald`'s default `max_batch_size` drops from 250 to 150; validators that set it explicitly keep their value.
5. Restart the validator node and `vald` with the new binaries. When restarting `axelard` do not do a rollback.
6. Please also upgrade any other Axelar nodes you operate (RPC nodes etc.).

## Troubleshooting

### `app hash` mismatch

The most likely cause is a stale `libwasmvm`. Confirm the loaded library is `v2.3.5`. Otherwise, make sure all replicas across your fleet were swapped to `v1.6.1` before the upgrade height; mixed binaries across replicas after the upgrade height will fork.

### `libwasmvm` errors with the dynamic binary

`libwasmvm` is **bumped from v2.3.4 (v1.5.x) to v2.3.5** in this upgrade. Replace the library on every dynamic-binary node before starting the new binary, otherwise it refuses to launch with a wasmvm version-mismatch error. Ensure `LD_LIBRARY_PATH` points at its location. For the Docker image and the `-static` binary no change is necessary.

### `vald` restarts right after the upgrade

`vald` requires the local `axelard` RPC to be reachable at startup and exits if it is not, so on nodes where `axelard` takes a while to open its store, `vald` may restart a few times with `unable to start client: dial tcp 127.0.0.1:26657: connect: connection refused` before settling. This is expected; it resolves once `axelard` is serving RPC.

### `RetryFailedMessage` / `RetryFailedEvent` rejected

From `v1.6.1` these are rejected while more than 30 messages are waiting to be routed, or more than 30 events are waiting on that chain. Wait for the queue to drain and retry.

### Rollback

This is a state-machine-breaking upgrade. **There is no in-place rollback** to `v1.5.x` once a node has executed the `v1.6` upgrade handler. The evm store migration and the parameter changes are persisted to state. Operators must restore from a pre-upgrade snapshot if rollback is required.
